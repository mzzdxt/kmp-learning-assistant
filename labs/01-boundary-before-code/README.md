# 实验 01：在写代码前画出跨平台边界

## 实验目的

用你已有的 Android 项目建立第一份“共享候选清单”。这个实验不需要安装任何工具，重点是改变分类代码的方式。

## 选择一个功能

选择一个中等规模、你非常熟悉的功能，例如登录、商品列表、收藏、草稿箱或离线缓存。不要选择整个 App。

## 第一步：列职责，不列文件

错误示例：`LoginActivity.kt`、`LoginViewModel.kt`。  
正确示例：校验手机号、保存 token、展示权限弹窗、跳转首页、记录登录事件。

## 第二步：填写边界表

复制下面的表到本文件下方或学习日志中：

| 职责 | 两端规则必须一致？ | 依赖平台 API？ | 变化原因 | 初步归属 | 理由 |
|---|---|---|---|---|---|
| 手机号格式校验 | 是 | 否 | 产品规则变化 | commonMain | 纯规则且应保持一致 |
| 安全保存 token | 目标一致，实现不同 | 是 | 系统安全能力变化 | 接口 + 平台实现 | Android Keystore / iOS Keychain |
| 返回手势 | 否 | 是 | 平台体验变化 | 原生 UI | 应尊重平台习惯 |

初步归属只能从下面选择：

- `commonMain`
- 共享接口 + 平台实现
- `androidMain` / `iosMain`
- Android/iOS 应用层或原生 UI
- 暂不确定，需要最小实验

## 第三步：找出第一个共享规则

它应满足：

- 输入和输出可以用普通 Kotlin 类型表达。
- 不依赖 `Context`、`Activity`、`ViewModel` 等 Android 类型。
- Android 与 iOS 对它的正确性定义相同。
- 可以用至少 3 组输入输出测试。

用伪代码写出来：

```kotlin
data class Input(/* ... */)
sealed interface Result

fun rule(input: Input): Result = TODO()
```

## 完成标准

- 至少列出 10 项职责。
- 每项都写出“变化原因”，而不只写“能不能共享”。
- 找到 1 个纯共同规则。
- 找到 1 个需要平台实现的能力。
- 找到 1 个明确不应共享的原生体验。

把结果保留下来。创建 KMP 工程后，我们会选中那个纯共同规则，让它先在 Android/JVM 测试中运行，再在 iOS 模拟器测试中运行。
