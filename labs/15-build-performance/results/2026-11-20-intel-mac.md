# PocketLab 构建性能基线：Intel Mac，2026-11-20

这份记录保存实验 15 的可复查结论。原始 Gradle 日志和编译报告可能包含本机路径、编译参数与环境信息，因此保留在被 Git 忽略的 `build/` 目录，不作为公开仓库内容提交。

## 环境

| 项目 | 值 |
|---|---|
| Host | macOS x86_64，12 logical cores，32 GB RAM |
| JDK | 17.0.10 |
| Gradle | 8.14.4 |
| Kotlin | 2.4.21 |
| AGP | 8.13.2 |
| Xcode | 26.5 |
| KMP modules | `domain`、`shared`、`androidApp` |
| Native runnable target | `iosX64` |

当前 macOS x64 Kotlin/Native host 已被弃用。这里的数据用于解释这台学习机上的构建组成，不应直接成为 Apple Silicon CI 的预算。

## 测量协议

- 使用 `scripts/benchmark-build.sh`，由 Ruby monotonic clock 测外部 wall time；
- 先预热 Gradle daemon，常规场景也预热 task outputs；
- 配置缓存的首次 store 与后续 reuse 分开记录；
- 相同场景使用完全相同的 tasks 和 Gradle 参数；
- no-op 场景取 3–5 次样本，不把一次偶然值写成普遍规律；
- clean/build-cache 场景每一步先执行 `clean`，并检查 Gradle 的 `FROM-CACHE`、`UP-TO-DATE`、`executed` 任务统计；
- Native forced rerun 使用 `--rerun-tasks`，避免把已有输出误当作编译速度；
- 测量期间不包含依赖下载和 Kotlin/Native toolchain 下载；
- 机器不是隔离的 benchmark runner，结果只代表量级与瓶颈方向。

## 配置缓存：把“配置阶段”与“任务执行”分开

### 只运行 `help`

| 状态 | 样本 | 平均 | 最小 | 最大 |
|---|---:|---:|---:|---:|
| configuration cache disabled | 5 | 1,245 ms | 1,191 ms | 1,324 ms |
| configuration cache store | 1 | 1,254 ms | 1,254 ms | 1,254 ms |
| configuration cache reuse | 5 | 916 ms | 882 ms | 930 ms |

在这个几乎没有业务任务的场景里，reuse 比 disabled 平均低约 26.4%。这最接近“只观察 Gradle 配置”的实验，但仍包含进程通信和极少量 task execution。

### 日常 JVM 开发任务

任务集合：

```text
:domain:jvmTest :shared:jvmTest :androidApp:testDebugUnitTest
```

| 状态 | 样本 | 平均 | 最小 | 最大 |
|---|---:|---:|---:|---:|
| configuration cache disabled | 5 | 1,663 ms | 1,530 ms | 1,718 ms |
| configuration cache store | 1 | 4,532 ms | 4,532 ms | 4,532 ms |
| configuration cache reuse | 5 | 1,024 ms | 949 ms | 1,165 ms |

reuse 比 disabled 平均低约 38.4%，但第一次 store 明显更慢。当前 no-op 任务统计为 49 actionable tasks，其中 2 executed、47 up-to-date。结论是“重复工作流获益”，不是“所有单次构建都会快 38.4%”。

### 单架构 Native Debug 链接 no-op

任务：`:shared:linkDebugFrameworkIosX64`

| 状态 | 样本 | 平均 | 最小 | 最大 |
|---|---:|---:|---:|---:|
| configuration cache disabled | 3 | 1,562 ms | 1,490 ms | 1,646 ms |
| configuration cache store | 1 | 1,612 ms | 1,612 ms | 1,612 ms |
| configuration cache reuse | 3 | 1,080 ms | 1,048 ms | 1,100 ms |

reuse 比 disabled 平均低约 30.9%。这里的所有编译、链接输出已经存在，所以它只证明配置复用对重复 Native task invocation 有价值，不代表 Native 冷编译只需一秒。

## 构建缓存：只看墙钟时间会得出错误结论

任务仍是日常 JVM 开发任务。权威的一次受控序列为：

| 步骤 | Wall time | 任务结果 | 含义 |
|---|---:|---|---|
| clean compile，关闭 build cache | 11,655 ms | 49 executed | 无可复用 task outputs 的参考值 |
| clean 后首次 cache population | 2,408 ms | 21 executed，28 from cache | 本机 cache 已有部分内容，不能叫“纯首次” |
| 再次 clean 后 warm restore | 1,510 ms | 21 executed，28 from cache | 28 个任务从 build cache 恢复 |
| 不再 clean 的 no-op | 1,039 ms | 2 executed，47 up-to-date | 本地 outputs 存在，up-to-date 更直接 |

第一轮试验曾得到 23,077 ms 对 11,911 ms。如果只看时间，可以草率地写成“build cache 快 48%”；但日志只有 1 个 `FROM-CACHE`，差异同时混入 daemon、配置并行度和机器状态，因此这组数字被否决。

这也是实验的关键结论：

> build cache 是否生效，先检查 task outcomes；wall time 只描述用户等待了多久，不能单独证明原因。

## Kotlin 编译报告：Native 时间花在哪里

强制重新执行：

```shell
./gradlew :shared:linkDebugFrameworkIosX64 --rerun-tasks
```

总 wall time 为 19.80 s。Kotlin build report 给出的任务分解：

| 指标 | 时间 |
|---|---:|
| 全部 Gradle task time | 19.758 s |
| Kotlin task time | 18.323 s（全部 task time 的 91.5%） |
| `domain:compileKotlinIosX64` | 5.355 s |
| `shared:compileKotlinIosX64` | 2.749 s |
| `shared:linkDebugFrameworkIosX64` | 9.955 s |
| SQLDelight interface generation | 1.665 s |

`linkDebugFrameworkIosX64` 内部主要阶段：

| 编译器阶段 | 时间 |
|---|---:|
| LinkKlibs | 3.267 s |
| compiler analysis | 5.385 s |
| backend | 3.337 s |
| IR lowering | 1.341 s |
| IR linking | 3.314 s |
| code generation | 1.513 s |
| object files | 0.588 s |
| native linker | 0.534 s |

这说明当前 Native forced build 的主要成本是 Kotlin/Native 编译和链接，不是 Gradle configuration。配置缓存能缩短重复调度，但不能消除必须完成的编译工作。

上一里程碑的真实 Release distribution gate 为三个架构组装 XCFramework，用时约 4 min 37 s。它与本次单个 `iosX64` Debug forced rerun 不是同条件 benchmark：target 数、build type、优化和产物都不同。它们只能共同说明开发循环不应默认运行完整 Release XCFramework。

本里程碑收尾时再次运行同一 distribution gate，在已有 Gradle cache/outputs 的状态下为 2 min 26 s：19 actionable tasks 中 8 executed、2 from cache、9 up-to-date。这个结果证明 warm regression gate 通过，不能与上一轮 cold/不同状态的 4 min 37 s 直接相除并归因给某一项配置。

## 实现改动与公共 ABI 改动

### 私有等价实现改动

将：

```kotlin
value.trim().length > maximumLength
```

临时改写为语义等价的：

```kotlin
value.trim().length >= maximumLength + 1
```

运行日常 JVM tasks 后：

- `domain` 的 JVM/Android compilation 执行；
- `shared` 的 JVM/Android compilation 保持 `UP-TO-DATE`；
- Android App compilation 保持 `UP-TO-DATE`；
- 依赖运行时 classpath 的 tests 重新执行；
- Kotlin report 标记 `Incremental compilation might be incorrect (KT-62686)`，对改动的 common source 执行非增量 compilation。

因此可以证明的是“module/classpath boundary 避免了下游重新编译”，不能证明“commonMain 文件被精确增量编译”。

当相同源码变体之前已经构建过，再切回该变体时出现 5 个 `FROM-CACHE`。这展示了 build cache 按 inputs/outputs 恢复结果，与 incremental compiler 在一次 task 内复用分析状态是两件不同的事。

### 新增公共方法

临时给 `DraftValidator` 增加 public `supportedFields()`，并使用 `--no-build-cache` 运行相同 tasks：

- 49 actionable tasks：17 executed、32 up-to-date；
- `domain:compileKotlinJvm` 与 `domain:compileAndroidMain` 执行；
- `shared:compileKotlinJvm` 与 `shared:compileAndroidMain` 执行；
- `androidApp:compileDebugKotlin` 执行；
- 三层相关 test compilation/tests 也执行。

公共 ABI 变化沿依赖图传播。模块边界能阻止不必要传播，但不能让真实的 ABI 依赖消失。两个临时改动都已还原，不属于产品代码。

## 本轮决策

启用并由门禁验证：

```properties
org.gradle.caching=true
org.gradle.configuration-cache=true
kotlin.build.report.output=file,json
```

保留按意图选择任务的工作流：

1. 日常领域/基础设施反馈：JVM tests；
2. Android 风险：Android host tests、App unit/UI；
3. Apple 开发：当前 host 的单一 Debug framework/test target；
4. 合并验证：全部可运行 targets；
5. 发布：Release XCFramework 与 distribution gate。

暂不启用：

- 更大 Gradle heap：没有 GC/OOM/内存压力证据；
- `kotlin.incremental.native=true`：仍为 Beta，尚无本项目 A/B 证据；
- Kotlin/Native Release binary cache flags：可能改变优化取舍，当前没有 Release runtime benchmark；
- remote build cache：需要可信度、访问控制、淘汰、成本和跨 runner 稳定性设计；
- 每次开发前 `clean`：它主动销毁 up-to-date outputs，只用于受控实验或诊断。

## 局限与复测条件

- clean/native 场景样本很少，不能用于跨机器排名；
- 这是小型项目，配置占比会随模块、插件和代码规模变化；
- 后台负载、文件系统 cache、daemon 状态会影响 wall time；
- 当前 Intel Native host 已弃用，迁移 Apple Silicon 后必须重建基线；
- 当前 Xcode 26.5 缺少匹配 runtime，无法在本轮重跑 iOS UI smoke；
- 本轮 JVM/Android Host/iOS x64 聚合为 39/39/47，Android unit/Compose UI 为 2/2、2/2，均无失败；
- 依赖、Gradle/Kotlin/AGP/Xcode、CI runner 或模块图变化时，应重新测量；
- CI 可设置趋势预算，但不应把本机单次毫秒值变成易抖动的硬门禁。
